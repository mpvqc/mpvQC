# Swap the Wayland inset on the compositor's resize

The inset of ADR 0003 is not constant. Maximized and fullscreen the app draws no frame, so the drop shadow margin goes
to zero and comes back on restore. The swap used to ride on the window-state signal, and that is the wrong moment in
both directions. Qt emits the signal synchronously when the app requests a state, before the compositor has answered,
and one queued event late when the compositor applies a state on its own. Swapped on the request, the margin shrank the
surface around the old content for a frame or two before the compositor's configure resized it again; KWin's maximize
effect snapshots the window on the request and cross-fades the snapshot into that shrunken frame, and the squeeze is
the visible jank. Restore mirrored it with a surface briefly larger than the screen. Swapped on the queued event, a
compositor-driven maximize — a shortcut, a drag to the top edge — committed one frame at the new size with the old
margin still in place.

One moment is both after the compositor has decided and before the frame at the new size renders: the resize itself.
Applying a configure, the Wayland platform window records the states the compositor applied, resizes the window
synchronously, and only then exposes it. So the surface controller syncs on the window's resize signals, and it reads
the states from the platform window, which already holds them, rather than from `QWindow`, which learns them from the
queued event. `QWaylandWindow::windowStates` is that read: private Qt API, reached the way the margin setter is, a
fourth mangled symbol in the same resolver. The platform tracks activation in the same flags and the read masks it off,
since `QWindow` never reports it. Off Wayland, or before the platform window exists, the read falls back to `QWindow`.

The state signal stays connected as a backstop. On the request path its synchronous emit sees the platform state
unchanged and does nothing; on the compositor path the queued event arrives after the resize has synced and does
nothing; it still covers a state change that moves no pixel, a window already at the work-area size.

Swapping the margin from inside the resize re-enters Qt's geometry change: the margin setter resizes the window again,
so the nested resize signals fire with the final size and the outer `heightChanged` is then delivered with an argument
from before the swap. `QWindow` itself is current throughout. So the main window service reads the size off the window,
never off the signal.

## The snapshot bridge keeps a squeeze

Synced on the resize, the transition is still not smooth where the desktop animates it. KWin and Mutter both bridge a
maximize by scaling a snapshot of the window's last image into the new frame, and the snapshot is taken when the
compositor processes the state change. The last image carries the drop shadow band, the maximized frame does not, so
the bridge squeezes the content by exactly the band's share — 1280/1456 of the width under an 88-pixel band, measured
frame-accurate on a screen capture — and that squeeze reads as the window shrinking before it grows.

No client-side move covers every path. An app-driven maximize can put a collapsed frame on the wire before its
request, since one connection processes requests in order. But a maximize the compositor starts — a shortcut, a drag
to the top edge — has no request to precede; the snapshot exists before the client hears anything. A collapse-first
handler for the app-driven half was built and dropped again: half a fix was not worth its moving parts.

So the band is sized to keep the squeeze under notice instead of fighting the bridge. GTK sits in the same spot and
ships a 25-pixel band, measured on its wire; at that width the bridge squeezes 1280-wide content to 0.96, where the
88-pixel band squeezed it to 0.88 in plain sight. The shadow blur plus spread must stay inside the band, so the shadow
replicates libadwaita's window box-shadow layer for layer, its one-pixel outline ring included.

## Consequences

- The first frame after a maximize or restore, whether the app or the compositor started it, is at the final size with
  the final margin. Measured on KWin: one synced frame per transition and no intermediate buffer.
- The resize signals are the sync trigger and the state signal is the backstop. Moving the sync back onto the state
  signal alone brings the shrink back.
- A slot on a window resize signal may be handed a stale size; read the window.
- A maximize that changes no size keeps the old margin for one frame, until the queued state event lands.
- The tiled states of half and quarter tiling are not among the states `QWindow` knows, so the margin stays when tiled.
- The fourth symbol lives and dies with the other three: generated by the same updater, failing as quietly, deleted
  under the same condition. Without it the read falls back to `QWindow` and the jank is back; nothing else breaks.
- The bridge squeeze stays on every maximize the desktop animates; the 25-pixel band keeps it under notice.
- The restore direction mirrors mildly: its snapshot is band-less and the restored frame is not, so a desktop that
  animates the restore draws the old content slightly past the frame, into the transparent band, while it fades.
